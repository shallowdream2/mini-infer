## 已完成阶段（Phase 1-5）

### Phase 1 ✅ 单卡最小推理链路（2026-03-19）

- 真实模型加载（Qwen2.5-7B-Instruct，float16，单卡 RTX 4090，15.7 GB）
- 最小 generate()：Prefill + 串行 Decode + EOS 检测
- HF baseline 对比：batch=1 持平（56 tok/s），batch=4/8 差 3.7×/7.3×
- **关键发现**：串行 decode 是批量推理的根本瓶颈

### Phase 2 ✅ Paged KV Cache + Continuous Batching（2026-03-19）

- Paged KV Cache（BlockTable + FreeBlockPool + block tensor 池）
- Prefill/Decode 分离，Batch Decode，Continuous Batching
- benchmark：batch=8 达到 HF 的 49.1%
- **关键发现**：gather_batch_kv Python 循环是主要瓶颈

### Phase 3 ✅ 向量化 gather + DynamicCache（2026-03-19）

- gather_batch_kv 向量化（PyTorch advanced indexing）
- DynamicCache API 迁移
- benchmark：batch=8 从 49.1% → 88.4% HF
- **关键发现**：gather 降至 1.8%，还差 12% 根因未明

### Phase 4 ✅ 双卡扩展（2026-03-19）

- ReplicaEngine（两卡数据并行）+ TPEngine（HF Pipeline Parallel）
- benchmark：Replica batch=8 仅 +4.1%，PP 吞吐持平但每卡显存减半
- **关键发现**：RTX 4090 在 batch=4~8 已接近 GPU 饱和，数据并行收益有限

### Phase 5 ✅ Profiling + 项目收尾（2026-03-19）

- torch.profiler 量化 decode_batch 三段（gather_kv / model_forward / write_kv）
- 结论：model_forward 占 97-98%；gather 降至 1.5-1.8%；存在 ~3.6ms/step 无标签 CUDA 时间
- **关键发现（直接指导 Phase 6）**：
  - 三个标签操作合计 18.4ms/step，但总 CUDA 时间 ~22ms/step，差 ~3.6ms 无标签
  - HF baseline 每步也做 28× DynamicCache.update()，但它在 model_forward **内部**完成；mini-infer 在 model_forward **之前**预填充（纯 Python list append，无 GPU 开销）
  - 因此 12% 差距的真实来源：gather（0.31ms）+ write_kv（0.19ms）+ attention_mask 左填充额外计算 + Python 调度开销
  - **PyTorch SDPA flash_sdp 已启用**：HF model 推理时已在用 FlashAttention kernel

## 未来阶段规划

### Phase 6 ✅ True PagedAttention（flash_attn 2.5+ block_tables）（2026-03-20）

**实际结果**：batch=8 throughput **406.3 tok/s = 100.0% HF baseline**（预期 90-95%，超出预期）。gather_batch_kv 和 write_decode_kv 完全消失。关键教训：`.item()` 在 28 层各调用一次 = 28× CPU-GPU sync = 504ms/step，是性能问题不是正确性问题，只有 profiler 才能发现。

#### 动机与技术背景

Phase 5 profiling 揭示了关键事实：

**当前 mini-infer decode 路径（每步）：**
```
block tensor → gather_batch_kv(0.31ms) → k_batch[28层]
                                               ↓
                              DynamicCache 预填充（28层 list.append，Python-only，无 GPU 开销）
                                               ↓
model_forward(17.9ms) = Q/K/V proj × 28 + flash_sdp × 28 + 28× DynamicCache.update(k_new, v_new)
                                               ↓
                              write_decode_kv(0.19ms) → 写回 block tensor
```

**Phase 6 的目标路径（每步）：**
```
flash_attn_with_kvcache(q, k_cache[l], v_cache[l], k=k_new, v=v_new,
                        block_table=block_table, cache_seqlens=cache_seqlens)
  → 直接从 block tensor 寻址，in-place 写入新 KV，计算 attention
  → 无 gather，无 DynamicCache，无 write_kv
```

消除的开销（保守估计）：
- gather_batch_kv：0.31ms/step（确定消除）
- write_decode_kv：0.19ms/step（确定消除）
- attention_mask 相关开销（不再需要 attention_mask，flash_attn 用 cache_seqlens 处理变长）

额外可能消除的开销（取决于 flash_attn 实现）：
- 28× DynamicCache.update()（aten::cat）inside model_forward — HF 同样有此开销，Phase 6 用 flash_attn in-place 写入替代

**Phase 6 性能预期（保守）：**
- 确定提升：gather (0.31ms) + write_kv (0.19ms) = 0.5ms / 22ms ≈ **+2-3%**
- 额外提升（不确定）：如果 flash_attn_with_kvcache 比 flash_sdp + DynamicCache.update() 更快，可能再提升 1-5%
- **合理预期区间：90-95% HF baseline（当前 88.4%）**
- "Phase 6 可能超过 HF" 的说法过于乐观，不应作为验收标准

#### flash_attn 2.5+ PagedAttention API

```python
from flash_attn import flash_attn_with_kvcache

output = flash_attn_with_kvcache(
    q,                # (batch, 1, num_heads, head_dim)            — 当前 token Q
    k_cache,          # (num_blocks, block_size, num_kv_heads, head_dim) — 已有 k 块（in-place 会被写入）
    v_cache,          # 同上
    k=k_new,          # (batch, 1, num_kv_heads, head_dim)          — 当前 token K（写入 cache）
    v=v_new,          # 同上
    cache_seqlens=cache_seqlens,  # (batch,) int32 — 各请求当前 cache 长度
    block_table=block_table,      # (batch, max_blocks_per_seq) int32
    causal=True,
    softmax_scale=1.0 / math.sqrt(head_dim),
)
# output: (batch, 1, num_heads, head_dim)
# 副作用：k_cache 和 v_cache 被 in-place 更新（写入了 k_new 和 v_new）
```

flash_attn 2.5+ 有内置 RoPE 参数（`rotary_cos`, `rotary_sin`）。但 Qwen2.5 的 RoPE 实现与 flash_attn 内置格式可能不完全兼容，建议手动应用 RoPE：

```python

```

### Phase 7（已完成，参考下方详细规划）：Preemption + Priority Scheduling 📋 规划详情

#### 动机

当前调度器行为：KV 空间不足时立即抛 RuntimeError。真实推理服务需要优雅降级：将低优先级请求换出到 CPU，高优先级请求优先服务。这是 vLLM 调度系统的核心设计。

#### CPU-GPU 带宽约束（实现时必须测量）

swap_out/swap_in 会产生 PCIe 传输开销，这是 preemption 的真实成本：
- PCIe 4.0 ×16 带宽：~32 GB/s（单向）
- Qwen2.5-7B-Instruct：28 层 × 4 KV heads × 128 head_dim × float16 × 2（K+V）= 每个 token 约 57 KB
- 单请求 128 token：KV 约 7 MB → swap_out 延迟 ~0.2ms（理论最优）
- 实际延迟更高（CPU pin memory、Python 调度开销）

**benchmark 要求**：Phase 7 的 benchmark 必须包含：
1. swap_out 和 swap_in 的实际延迟（用 CUDA event 计时）
2. 有 preemption 场景和无 preemption 场景的吞吐对比（量化 swap 代价）

> **注意**：不要求"不同 swap 频率下吞吐的变化曲线"——那是生产系统调优的工作量，超出学习阶段的合理范围。验收重点是**正确性**（换出换入后生成结果一致）和**基础延迟测量**（swap 的实际开销是多少）。

**新增 RequestStatus 状态机：**

```python
    WAITING = "waiting"
    RUNNING = "running"
    SWAPPED = "swapped"   # KV 已换出到 CPU，等待换回
    FINISHED = "finished"
```

**KVCacheManager 新增接口：**
```python
def swap_out(self, state: RequestState) -> None:
    """将 GPU KV 拷贝到 CPU tensor，释放 GPU 块。"""
    # 在 state 上存储 cpu_kv: list[tuple[Tensor, Tensor]]  （每层的 k, v CPU 副本）
    # 释放 GPU 块 → free_request(state)

def swap_in(self, state: RequestState) -> None:
    """重新分配 GPU 块，将 CPU KV 拷贝回 GPU，清除 cpu_kv。"""
```

**Scheduler 改造：**
- `RequestState` 新增 `priority: int`（越小优先级越高）和 `status: RequestStatus`
- `Scheduler` 新增 `_swapped: deque[RequestState]`
- 准入失败时：evict `running` 中 priority 最低的请求（swap_out），准入新请求
- 每步主循环结束后：尝试 swap_in（有空闲块时）

**Engine 主循环改造：**
```python
# 准入逻辑中：
if not enough_blocks:
    victim = scheduler.get_lowest_priority_running()
    if victim and victim.priority > new_state.priority:
        kv_cache.swap_out(victim)
        scheduler.mark_swapped(victim)
        # 现在有足够块了，准入新请求
```

**核心设计挑战：** LLMEngine 是同步的，FastAPI 是异步的，且存在并发请求合并问题：

```
❌ 错误设计：每个 HTTP 请求在独立线程里调用 engine.generate([prompt])
   → 两个并发请求会各自独占 GPU，互相竞争，不是 continuous batching

✅ 正确设计：HTTP 请求将 prompt 放入队列，后台线程持续运行 engine step 循环
   → 不同 HTTP 请求的 prompt 被 continuous batching 合并到同一个 batch
   → 每条请求通过 asyncio.Future 异步等待结果
```

正确的 async 包装架构：
```python
# 后台线程：持续运行 engine step，不等待请求凑齐
def _engine_loop():
    while True:
        engine._step()  # 一次 prefill + decode_batch

# HTTP handler：提交 prompt，等待 Future 完成
async def completions(request):
    future = asyncio.get_event_loop().create_future()
    await queue.put((request.prompt, future))
    return await future
```

这个并发设计问题本身是面试常考题，理解它比实现它更重要。

#### 理论基础（infer-plan 时需要掌握）

**Roofline analysis for decode attention on RTX 4090：**
- GPU 峰值带宽：1008 GB/s；峰值算力：82.6 TFLOPS
- 临界算术强度（ridge point）：82.6T / 1008G ≈ 82 FLOPs/Byte
- Decode attention（seq_len=128，batch=8，4KV heads，head_dim=128，fp16）：
  - 每步读 K/V：2 × batch × seq_len × num_kv_heads × head_dim × 2bytes ≈ 8×128×4×128×2 = 1MB
  - 每步计算（QK matmul + softmax + AV matmul）：约 2×batch×num_heads×seq_len×head_dim = 8×28×128×128×2 = ~7.4M FLOPs
  - 算术强度 ≈ 7.4M / 1M ≈ **7.4 FLOPs/Byte**，远低于 ridge point（82）
  - 结论：**decode attention 是 memory-bound**，优化目标是最大化 bandwidth utilization，而非减少 FLOPs
- 达到峰值带宽 60% 的 kernel（~600 GB/s）是可接受的最低性能目标

**Triton 编程模型关键概念（必须在开始前理解）：**
- `@triton.jit` + `tl.constexpr`：kernel 编译时常量（tiling size 必须是 constexpr）
- `tl.load / tl.store`：向量化访存，每次操作 BLOCK 个元素
- Shared memory（SRAM）：Triton 自动管理，通过 `tl.dot` 触发 tensor core，数据必须在 SRAM 里
- Block pointer：`tl.make_block_ptr` 更安全的访存方式（Triton 2.0+）
- Attention 特殊性：需要 softmax（online softmax，Milakov&Gimelshein 算法），不能分两步

### Phase 9：Chunked Prefill ✅（2026-03-21 完成）

**实测结果**：chunk=256 时 ITL spike −57.5%（138ms→59ms），TTFT +132ms，吞吐无回归。
详细见 `本地资料/实验记录/2026-03-21-phase9-benchmark.md`。

#### 动机

当前调度模型：每个 step 最多接入一个新请求并完成其**完整** prefill，prefill 期间整个 decode batch 被阻塞。对于长 prompt（512+ tokens），一次 prefill 耗时 10-50ms，所有 decode 请求在此期间完全停滞，TTFT 对并发请求造成严重影响。

Chunked Prefill 的解法：将一次 prefill 拆成多个 chunk，每个 step 只处理一个 chunk，同时继续 decode 其他请求，长 prefill 对 decode 请求的干扰从"一次性大块"变成"多次小块"。

```
当前（无 chunked prefill）：
  step 0: prefill(1024 tokens, req_A)  →  decode batch 阻塞 ~50ms
  step 1: decode([req_A, req_B, ...])

Chunked Prefill（chunk_size=256）：
```

### Phase 11：Speculative Decoding（已完成）

状态更新（2026-03-22）：已完成。实际实现、benchmark 和收尾结论见 `本地资料/里程碑总结/13-Phase11-里程碑总结-2026-03-22.md` 与 `本地资料/实验记录/2026-03-22-phase11-benchmark.md`。以下内容保留原始规划与验收口径，供回顾参考。

#### 动机

Decode 是 memory-bandwidth bound（Phase 6.5 roofline 已量化，AI ≈ 7 FLOPs/Byte）。每步只产生 1 个 token，GPU 算力利用率极低。

Speculative Decoding 的核心思路：用小而快的 draft model 一次性预测 K 个 token，再用大的 target model **一次 forward** 并行验证 K+1 个位置。验证的计算量与验证 1 个 token 相近（同样是 memory-bound），但一次性确认了多个 token，有效吞吐倍增。

**理论加速比**（modified rejection sampling）：

```
α = 每个 draft token 的平均接受率
E[接受长度] = (1 - α^K) / (1 - α)
加速比 ≈ E[接受长度] / (1 + draft_cost_ratio)

对 Qwen2.5-0.5B → 7B：draft_cost_ratio ≈ 0.5/7 ≈ 0.07
α=0.7, K=4 时：E[接受长度] ≈ 2.76，加速比 ≈ 2.58×
```

#### 算法：Modified Rejection Sampling

```python
def speculative_sample(draft_tokens, draft_probs, target_probs):
    """
    保证输出分布 = target model 的分布（无偏）。
    draft_tokens: [K] 个 draft 预测的 token id
    draft_probs:  [K, vocab_size] draft 概率
    target_probs: [K+1, vocab_size] target 对 K+1 个位置的概率
    """
    accepted = []
    for i, token in enumerate(draft_tokens):
        accept_prob = min(1.0, target_probs[i, token] / (draft_probs[i, token] + 1e-10))
        if random.random() < accept_prob:
            accepted.append(token)
        else:
            # 从修正分布重采样（保证无偏）
            residual = torch.clamp(target_probs[i] - draft_probs[i], min=0)
            new_token = sample_from(residual / residual.sum())
            accepted.append(new_token)
            break
    else:
        # 全部接受，再从 target_probs[K] 采最后一个 bonus token
        accepted.append(sample_from(target_probs[K]))
    return accepted
```

### Phase 12：CUDA Graph（已完成）

状态更新（2026-03-22）：已完成。实际实现、benchmark 和收尾结论见 `本地资料/里程碑总结/14-Phase12-里程碑总结-2026-03-22.md` 与 `本地资料/实验记录/2026-03-22-phase12-benchmark.md`。以下内容保留原始规划与验收口径，供回顾参考。

#### 动机

即使 model_forward 只需 17ms，其中仍有约 0.5-1ms 是 Python→CUDA dispatcher 的 CPU 调度开销（每层的 kernel launch、tensor dispatch）。

CUDA Graph 将整个 decode step 录制为静态 CUDA kernel 序列，后续 step 直接"回放"图，绕过所有 Python dispatch。预期节省 5-15% decode 时间。

**静态 shape 约束与解决方案（Graph Pool）**：

CUDA Graph 要求录制与回放时 tensor shape 完全相同。Dynamic batching 中 batch size 变化，解决方案是为每个支持的 batch size 录制一个图：

```python
graph_pool = {}   # batch_size → CUDAGraph

# warmup 阶段（引擎启动时）
for bs in [1, 2, 4, 8]:
    graph_pool[bs] = capture_decode_graph(bs)

# decode 时
def decode_with_graph(actual_bs):
    padded_bs = min(s for s in graph_pool if s >= actual_bs)
    update_static_inputs(actual_bs, padded_bs)   # copy_ 数据，不改 shape
    graph_pool[padded_bs].replay()
    return extract_outputs(actual_bs)
```

#### 关键兼容性问题

| 问题 | 处理方式 |
|------|---------|
| Chunked prefill（动态 shape）| prefill steps 走 eager 模式，只有 decode-only steps 走 graph |
| Prefix caching（动态 block 分配）| block_table 作为静态 buffer，每次 replay 前 copy_ 更新内容 |
| Preemption（swap 触发 batch 缩小）| 动态 batch size 通过 graph pool 的 pad 策略处理 |

#### 实现范围

| 文件 | 改动 |
|------|------|
| `mini_infer/model_runner.py` | capture_decode_graph()，decode_with_graph()，static input buffer 管理 |
| `mini_infer/engine.py` | warmup 阶段触发 graph capture，decode step 切换到 graph replay |
| `benchmarks/benchmark_cuda_graph.py`（新建）| 逐 batch size 的 decode step 延迟对比（eager vs graph）|

### Phase 12.5：Flash Decoding（Split-K Attention）

#### 动机

Flash Attention 的 grid = (batch, num_heads)。对于 decode 场景（batch=1），grid 只有 28 个 thread block，而 RTX 4090 有 128 个 SM，利用率不足 22%。

Flash Decoding 在 KV 序列长度方向再切分（split-K），grid 变为 (batch, num_heads, num_splits)，SM 利用率随 seq_len 线性提升。

**收益条件**：seq_len > 2048 时效果明显；seq_len < 512 时与 flash_attn 差距不大。

#### 技术实现

扩展 Phase 6.5 的 Triton kernel，增加 split-K 维度：

```
第一步 kernel：_flash_decode_split
  grid = (batch, num_heads, num_splits)
  每个 program 处理 KV[split_start : split_end]
  输出：partial_out[batch, num_heads, num_splits, head_dim] 和 partial_lse（log-sum-exp）

第二步 kernel：_flash_decode_reduce
  grid = (batch, num_heads)
  在 split 维度上合并 partial outputs（online softmax 归约）
  输出：最终 out[batch, num_heads, head_dim]
```

#### 验收标准

1. seq_len=2048 时，Triton split-K 延迟 ≤ flash_attn_with_kvcache
2. seq_len=4096 时，有明显提升（目标 < 0.5× flash_attn）
3. 数值正确性：max_diff < 1e-2 vs flash_attn

#### 跳过/降级条件

- 如果 split-K 归约的数值稳定性无法保证（> 1 周），跳过
- 如果 RTX 4090 上实测对实际 seq_len 范围没有收益，记录原因后跳过

### Phase 13：Tensor Parallelism（真 TP，NCCL）

#### 动机

Phase 4 的 PP 是层间串行，吞吐不提升。真正的 Tensor Parallelism（TP）将 attention heads 和 FFN neurons 切分到多卡：

- **Column Parallel**（Q/K/V/gate/up projections）：沿输出维度切分，每卡处理 num_heads / TP_SIZE 个头
- **Row Parallel**（O/down projections）：沿输入维度切分，forward 后需要 NCCL all-reduce
- **KV cache**：每卡只存自己负责的 KV heads

TP 的核心价值：70B+ 模型必须用 TP 才能在多卡上服务单个请求。

#### Qwen2.5-7B TP=2 切分方式

```
原始尺寸：
  q_proj: 3584 → 28×128=3584（28 Q heads）
  k_proj: 3584 → 4×128=512（4 KV heads，GQA）
  v_proj: 3584 → 4×128=512
  o_proj: 3584 → 3584

TP=2 后（每卡）：
  GPU0: q_proj → 14 Q heads，k_proj → 2 KV heads，v_proj → 2 KV heads
  GPU1: q_proj → 14 Q heads，k_proj → 2 KV heads，v_proj → 2 KV heads
  两卡各做 partial attention，o_proj 后 all-reduce 合并
```

#### 技术实现

```python
import torch.distributed as dist

class TensorParallelModelRunner:
    def __init__(self, config, tp_size=2):
        dist.init_process_group("nccl")
        self.rank = dist.get_rank()
        self.tp_size = tp_size
        self._shard_weights()   # 按 rank 切分模型权重

    def _shard_weights(self):
        for layer in self.model.model.layers:
            # column parallel：只保留本 rank 的列切片
            layer.self_attn.q_proj.weight = col_shard(q_w, self.rank, self.tp_size)
            layer.self_attn.k_proj.weight = col_shard(k_w, self.rank, self.tp_size)
            # row parallel：只保留本 rank 的行切片（forward 后 all-reduce）
            layer.self_attn.o_proj.weight = row_shard(o_w, self.rank, self.tp_size)
            # FFN 同理：gate/up column parallel，down row parallel

    def decode_batch(self, ...):
        out = self._forward(...)            # 每卡各自 partial forward
        dist.all_reduce(out, op=dist.ReduceOp.SUM)   # row parallel 后 all-reduce
        return out
```

### Phase 14：MLA（Multi-head Latent Attention）

#### 动机

DeepSeek-V2/V3/R1 用 MLA 将 KV cache 压缩到低秩空间：

```
标准 GQA（Qwen2.5-7B）：KV per token ≈ 57 KB（28 layers × 8 KV bytes × 128 head_dim × 4 heads × 2）
MLA（DeepSeek-V2）：KV per token ≈ 32 KB（latent_dim=512 + rope_dim=64，2 bytes × 28 layers）
```

MLA 允许在相同显存下服务约 1.8× 更多并发请求。

#### MLA 数学结构

```
标准 MHA：
  K = X × W_k，V = X × W_v

MLA：
  C_KV = X × W_dkv                    # 低秩压缩（dim(C_KV) << dim(K)）
  K_content = C_KV × W_uk             # 从 latent 解压 K（non-RoPE 部分）
  K_rope = X × W_kr（+ RoPE）         # K 的 RoPE 部分
  V = C_KV × W_uv

  优化（矩阵吸收）：
  W_q × W_uk 可预计算，推理时不需要显式解压 K_content
  → 实际只需缓存 C_KV（低秩 latent）+ K_rope
```

### Phase 15：Disaggregated Prefill/Decode（PD 解耦）

#### 动机

Prefill（compute-bound）和 Decode（memory-bound）在统一部署中互相干扰：prefill 阻塞 decode 导致 TTFT 抖动，decode 占用 GPU 让 prefill 吞吐下降。

PD 解耦的思路（Mooncake/Splitwise 架构）：
- **Prefill 节点**：只做 prefill，GPU 高算力利用率，吞吐最大化
- **Decode 节点**：只做 decode，延迟最小化
- **KV 传输**：prefill 完成后将 KV blocks 通过网络传输到 decode 节点

Phase 15 目标：同机多进程原型（不要求真正多节点），验证架构正确性。

#### 技术实现（同机多进程）

```
进程 A（Prefill Worker）：
  LLMEngine（prefill-only）
  prefill 完成后 → KVTransfer.send(state, decode_addr)

进程 B（Decode Worker）：
  LLMEngine（decode-only，接收已有 KV）
  KVTransfer.recv(request_id) → 加入 decode 调度

进程 C（Router）：
  接收 HTTP 请求
  → 路由到 prefill worker
  → 等待 KV 传输完成信号
  → 路由到 decode worker
  → 返回生成结果
```

**KV 传输接口**：

```python
class KVTransfer:
    def send_kv(self, state: RequestState, dst_addr: str) -> None:
        """序列化 state 的所有 KV blocks，通过 socket/共享内存发送。"""

    def recv_kv(self, request_id: str) -> RequestState:
        """接收 KV blocks，重建 RequestState，加入 decode engine。"""
```

#### 验收标准

1. 端到端请求跨两个进程完成，生成结果正确
2. KV 传输延迟可量化（目标：< 10ms for Qwen2.5-7B 128-token KV，同机共享内存）
3. TTFT 可分解：prefill_time + transfer_time + first_decode_time
4. Prefill 节点吞吐高于统一部署（不被 decode 干扰）

#### 跳过/降级条件

- 这是整个路线图风险最高的 Phase：
  - 如果跨进程 KV 传输超过 2 周无法稳定，降级为只实现 KV 传输原型（不接完整 scheduler）
  - 如果三进程协调逻辑复杂度超出合理范围，降级为详细架构设计文档（协议设计 + 带宽分析 + scheduling 算法），而非代码实现

#### 依赖

- 全部前序 Phase（需要最稳定的 engine 基础）
