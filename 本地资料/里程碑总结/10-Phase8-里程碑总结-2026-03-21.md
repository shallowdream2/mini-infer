## 四、遇到的问题

### 问题 1：竞态条件（已修复）

**现象**：第一版 AsyncEngine 在 `add_request()` 后才注册 token queue，背景线程可能在 queue 注册前就调用 `_put()` 投递 token，导致 token 丢失。

**修复**：生成 `rid` → 注册 `_token_queues[rid]` → 调用 `add_request(request_id=rid)`，确保 queue 先于请求存在。

### 问题 2：serve.py 默认 block_size=16（阻塞性，已修复）

**现象**：`python serve.py --model /path/to/model` 不带 `--block-size` 时，启动即报 ValueError（LLMEngine 要求 block_size % 256 == 0）。

**根因**：argparse 默认值 `default=16` 覆盖了 `EngineConfig.block_size` 的合理默认值 256。

**修复**：`default=16` → `default=256`。

### 问题 3：step() 真实路径返回空字符串（核心 Bug，在 benchmark 阶段发现）

**现象**：benchmark 首次运行 throughput = 0 tok/s，诊断发现 `step()` 返回 `{'rid': ['', '']}` 全为空串。

**根因**：`model_runner.prefill()` 和 `decode_batch()` 在真实 GPU 路径中始终调用 `append_generated(token_id, "")`，因为逐 token decode 对中文多字节字符会返回空串。而 `generate()` 在末尾做批量 decode，不受影响。`step()` 依赖 `generated_text_parts` 这一空数组，导致 HTTP API 无法生成任何文本。

**为什么测试未发现**：所有测试使用 `dry_run=True`，`_StubTokenizer.decode` 返回 `" [1] [2]..."` 格式，掩盖了真实 GPU 路径的问题。

**修复**：`step()` 中改用增量 tokenizer decode：
```python
old_text = decode(tok_ids[:pre], skip_special_tokens=True)
new_text = decode(tok_ids[:curr], skip_special_tokens=True)
delta = new_text[len(old_text):]
```

**教训**：干跑（dry_run）测试只能验证逻辑流程，不能验证真实路径的文本质量。对于涉及 tokenizer decode 的功能，必须补充 GPU 路径的集成测试。

### 问题 4：Pydantic v1 兼容性（已绕过）

**现象**：Pydantic 1.10.13 没有 `.model_dump_json()` 方法，只有 `.json()`。

**修复**：使用 `.json()` 替代。

## 五、Benchmark 结果

数据来源：`本地资料/实验记录/2026-03-21-phase8-benchmark.md`

**环境**：Ubuntu 24.04 + RTX 4090 × 1，Qwen2.5-7B-Instruct，block_size=256，max_tokens=64

| 指标 | 值 | 口径说明 |
|------|----|---------|
| TTFT（近似） | ~1157ms | 近似值（等于单请求总延迟），非真实首 token 延迟 |
| TPOT（近似） | ~18.5ms/tok | 总延迟 / 输出 token 数 |
| 峰值显存 | 23.34 GB | 与 Phase 6/7 完全相同 |
| 吞吐（并发=1） | 55.7 tok/s | tokenizer.encode 精确计算 |
| 吞吐（并发=2） | 105.0 tok/s | — |
| 吞吐（并发=4） | 193.6 tok/s | — |
| 吞吐（并发=8） | **351.4 tok/s** | — |

**Phase 6 直接 LLMEngine 参考**：batch=8，max=128 → ~406 tok/s

差距（351.4 vs 406）主要来自 workload 差异（max_tokens=64 vs 128），HTTP 层本身开销可忽略不计。
