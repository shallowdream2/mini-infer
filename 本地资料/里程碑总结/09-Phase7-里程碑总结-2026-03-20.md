# Phase 7 里程碑总结 — Preemption + Priority Scheduling

本文总结 mini-infer Phase 7 的目标、实现、遇到的问题和实测数据，作为阶段收尾的落盘记录。

---

## 一、阶段目标

在 Phase 6.5（Triton kernel）完成后，Phase 7 新增两项调度能力：

1. **Preemption（抢占/换出）**：当 GPU KV cache 空间不足时，将低优先级请求的 KV tensor 从 GPU 换出到 CPU，腾出空间给高优先级请求；换出后的请求在 GPU 空闲时换回（swap_in）继续生成。
2. **Priority Scheduling（优先级调度）**：请求可携带优先级字段，调度器按优先级决定换出顺序（先换最低优先级）。

|---|----------|------|------|
| 1 | num_gpu_blocks 很小时，低优先级请求被换出，新请求继续运行，不再 error | **达成** | `test_preemption.py` 中 `TestEnginePreemption` 全部通过；dry_run 测试覆盖该场景 |

## 三、关键成就

### 3.1 发现并修复了 never-prefilled 请求的 crash bug

**问题**：在 admission 循环中，一个请求刚被准入（`add_to_running`），但尚未 prefill（`prefilled == False`），就因 KV 空间不足被选为换出 victim。原逻辑调用 `swap_out`，后者会 `free_request` 清空 `_block_tables`，但该请求还在 `newly_admitted` 列表中。后续 `write_prefill_kv` 访问 `_block_tables[request_id]` 时触发 **KeyError crash**。

**修复**：在 engine 的 eviction 路径中根据 `victim.prefilled` 做分支：
- `prefilled == False` → `free_request + un_admit + newly_admitted.remove()`（撤销准入，归还块，放回 waiting 队尾）
- `prefilled == True` → `swap_out + mark_swapped`（KV 有效，正常换出）

**掩盖原因**：dry_run 模式下 `write_prefill_kv` 有 `if self._dry_run: return` 早返回，导致该 bug 在 dry_run 测试中不可见，只有真实 GPU 路径才会触发。

### 3.2 调度器 swap 延迟可忽略不计

纯元数据操作（dict + deque）swap_out 中位延迟 **0.36 µs**，swap_in **0.60 µs**，对 20 ms/step 的 decode 场景影响比例 < 0.005%。

### 3.3 吞吐无回归

同 batch_size 下，priority scheduling 路径 vs 无优先级路径：吞吐差异 **-0.0%**（198.3 vs 198.2 tok/s），符合预期（调度层变更不影响 decode forward）。

### 3.4 PCIe swap 带宽特性量化

实测 GPU↔CPU swap 有效带宽 ~**1050–1150 MB/s**，远低于 PCIe 4.0 x16 峰值（~32 GB/s）。根因：Python 层逐块循环 + 每次 `.cpu()` 触发独立 PCIe 传输 + CUDA sync。

对于 seq_len=256 请求（14.7 MB KV），swap 耗时 ~13.5 ms（约 0.5–1 个 decode step 当量）。与 vLLM 的一次性大块合并拷贝相比有明显差距，但本项目目标是展示原理，不是工程性能优化。

## 四、遇到的问题

### 4.1 never-prefilled 请求 crash（阻塞性，已修复）

见 3.1。

### 4.2 benchmark_preemption.py block_size 问题

原始版本 `BLOCK_SIZE=16` 会导致 `flash_attn_with_kvcache` 在吞吐测试中失败（需要 256-aligned block_size）。修复：为吞吐测试单独设 `GPU_BLOCK_SIZE=256`，swap latency 测试保留 `block_size=16`（不经过 flash_attn）。

### 4.3 真实 swap 路径的端到端验证受限

`generate()` API 要求所有请求同时提交，导致无法方便地演示"已 prefill 请求被 swap_out 后恢复"的完整 GPU 路径。该场景的正确性通过 dry_run 层面的单元测试验证；延迟数据可从 swap 延迟表推算。这是 API 设计的结构性限制，不影响主链路的正确性。
