## 关键成就

### Profiling 数据（RTX 4090，Qwen2.5-7B-Instruct float16，decode 30 steps）

| batch | gather_kv (ms/step) | model_forward (ms/step) | write_kv (ms/step) | model_forward 占比 |
|-------|--------------------|-----------------------|-------------------|-------------------|
| 1 | 0.272 | 17.274 | 0.023 | **98.3%** |
| 4 | 0.323 | 17.949 | 0.183 | **97.3%** |
| 8 | 0.314 | 17.890 | 0.193 | **97.2%** |

### 核心发现

**1. model_forward 支配 97-98% 的 decode CUDA 时间**

三种 batch size 下 model_forward 均值几乎相同（17.3～18.0ms/step），说明 RTX 4090 的 CUDA 核利用率在 batch=4~8 已趋近饱和，进一步加大 batch 的边际计算收益递减。

**2. Phase 3 向量化 gather_kv 的效果得到量化确认**

gather_batch_kv 从 Phase 2 的"主要瓶颈"降至 1.5-1.8%（0.27-0.32ms/step）。Phase 3 将逐请求 Python 循环改为 PyTorch advanced indexing 后，gather 不再是吞吐瓶颈，且 batch=4→8 的 gather 时间几乎不变，伸缩性好。

**3. write_decode_kv 可忽略（0.1-1.1%）**

不是优化目标。

**4. 残余 12% 差距的根因**

理论上 model_forward 占 97-98%，这 97% 本身就是"正确"的工作，其内部仍然有提升空间：
- **gather 物理拷贝**：gather_batch_kv 虽然向量化，但仍然需要把 block tensor 中分散的 KV 拷贝成 dense tensor 传给 Transformer。消除这层拷贝需要 flash_attn 2.5+ 的 block_tables 参数（attention kernel 直接从 block tensor 按地址读取），目前不在 mini-infer 实现范围内。
- **batch=1 的 GEMV 瓶颈**：batch=1 decode 本质是矩阵-向量乘，受限于显存带宽，与 batch 更大时的 GEMM 路径不同，HF 的实现也同样受此限制。

**5. kernel 变化规律**

- batch=1：gemvx（GEMV）内核主导，89.5% CUDA 时间，显存带宽瓶颈
- batch≥4：cutlass WMMA（GEMM）内核主导，89-90% CUDA 时间，compute-bound；FlashAttention FMHA kernel 激活

新 README 包含：4 阶段性能对比表、双卡扩展数据、架构说明、profiling 工具使用方法、phase by phase 状态一览。

## 问题与风险

### 已解决

- `profile_decode.py` 字段名拼写错误（review 发现，implement 修复）

### 已知局限

1. **Phase 3 剩余 12% 差距未解决**：gather 物理拷贝是结构性限制，需要 flash_attn 2.5+ 才能消除，不在本项目目标范围内。
2. **Profiling 含 profiler 自身开销**：torch.profiler tracing 对 CUDA 有额外 recording 代价，profiling 数据与正常 benchmark throughput 存在差异（以 `benchmark_mini.py` 数据为准）。
3. **更长序列的 gather 开销未测**：本次 profile 的 decode_steps=30，序列较短，KV 长度约 50-90 tokens。更长序列（500+）下 gather 的时间会线性增加，届时 gather 占比可能从 1.8% 上升到更高。
