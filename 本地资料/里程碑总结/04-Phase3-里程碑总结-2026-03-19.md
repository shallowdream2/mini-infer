# Phase 3 里程碑总结

本文件记录 mini-infer Phase 3（性能优化）的完整阶段复盘。

---

## 背景与目标

Phase 2 跑通了 Paged KV Cache + Batch Decode + Continuous Batching，但存在两个明显瓶颈：

1. **gather_batch_kv() 嵌套 Python 循环**：每次 decode step 需要 3 层循环（layer × batch × block），Python 解释器开销随 batch size 线性放大，batch=8 时 throughput 仅 201 tok/s，是 HF baseline 的 49.1%。
2. **transformers 弃用警告**：`past_key_values` 以 tuple 格式传入时 transformers 4.40+ 持续发出 UserWarning，影响日志可读性，且与新版 API 不兼容。

Phase 3 目标：
- 向量化 `gather_batch_kv()`，消除 Python 循环开销
- 迁移 DynamicCache API，消除弃用警告
- 新增混合长度 benchmark，体现 continuous batching 在异质请求下的调度行为

验收标准：
- batch=8 throughput 相比 Phase 2 提升 ≥30%（Phase 3 实际：+79.8%）
- 运行时无 UserWarning（已验证）
- 新增 `--mixed` benchmark 模式可运行（已验证）

---

## 已完成内容

### 代码变更

**`mini_infer/kv_cache.py` — gather_batch_kv 向量化**

用 PyTorch advanced indexing 替代 3 层嵌套 Python 循环：
1. 构建 `block_table_tensor [batch, max_num_blocks]`
2. 计算带左填充偏移的 `token_positions [batch, max_seq_len]`
3. 推算 `block_indices` 和 `slot_indices`（填充区 clamp 到 0）
4. 一次 `k_cache[l][phys_blocks, slot_indices]` advanced indexing 完成 gather
5. 乘以 `valid_mask_f` 置零填充位
6. permute 到 `[batch, num_kv_heads, max_seq_len, head_dim]`

**`mini_infer/model_runner.py` — DynamicCache 迁移**

- `from transformers import DynamicCache` 移至文件顶部
- `prefill()`：改为传 `past_key_values=DynamicCache()` 给模型，使模型返回 DynamicCache 而非 tuple（消除 transformers 4.43.4 在 prefill 阶段内部触发的 tuple 弃用警告）
- `decode_batch()`：构造 `DynamicCache` 并通过 `cache.update(k, v, l)` 填充后传入模型；从 `out.past_key_values.key_cache[l]` 提取新 KV

**`tests/test_kv_cache.py` — gather 正确性测试**

新增 `test_gather_batch_kv_correctness()`：
- 使用 `device="cpu"`, `dry_run=False`，不依赖 GPU
- 2 请求（req_a: seq_len=6，req_b: seq_len=3），验证左填充精确值和 padding 置零

**`benchmarks/benchmark_mini.py` — 混合长度 benchmark**

- 新增 `MIXED_WORKLOAD`：8 条请求（短 prompt × 4，max_new_tokens=32；长 prompt × 4，max_new_tokens=256）
- 新增 `MixedBenchmarkResult` dataclass（含 `short_prompt_count`、`long_prompt_count`、`actual_max_new_tokens` 字段）
- 新增 `benchmark_mini_mixed()` 函数和 `--mixed` CLI flag
- 修正标签：`engine_phase` 和打印文本统一更新为 Phase 3

## 关键成就

### 性能突破

| batch | Phase 2 | Phase 3 | 提升 | vs HF |
|-------|---------|---------|------|-------|
| 1 | 49.4 tok/s | 53.7 tok/s | +8.7% | 95.5% |
| 4 | 135.2 tok/s | 194.2 tok/s | +43.6% | 92.3% |
| 8 | 201.0 tok/s | 361.3 tok/s | +79.8% | 88.4% |

Phase 3 batch=8 throughput 从 Phase 2 的 49.1% HF 提升到 88.4% HF，基本追平。

### 工程质量提升

- `gather_batch_kv` 从 O(layers × batch × blocks) Python 循环 → 单次 CUDA kernel advanced indexing，无论 batch 多大 Python 层只有常数次调用
- DynamicCache 迁移彻底消除 transformers 弃用警告
- 新增 CPU-based 向量化 gather 正确性测试，逻辑可在无 GPU 环境验证

### 混合长度 benchmark 跑通

8 请求 mixed workload throughput 356.0 tok/s，Peak Mem 17.00 GB。

## 问题与风险

### 已解决

1. **DynamicCache 警告在 prefill 触发，不在 decode_batch**：根因是 transformers 4.43.4 在收到无 `past_key_values` 的调用时内部返回 tuple 并触发警告。修复：在 `prefill()` 中传 `DynamicCache()` 空实例。
2. **review 发现的 label 错误**：`benchmark_mini.py` 中 `engine_phase` 仍为 "mini-infer-phase2"，打印文本仍写 "Phase 2"，已全部修正。
3. **mixed benchmark 字段语义不清**：`short_req_count`/`long_req_count` 误导为请求已按短/长差异化执行，实际所有请求统一 `max_new_tokens=max(list)`。重命名为 `short_prompt_count`/`long_prompt_count` + `actual_max_new_tokens` 字段，打印明确说明。
4. **valid_mask_f dtype 隐患**：`valid_mask` 为 bool，直接乘 KV tensor 会触发 PyTorch 隐式类型转换，已加 `.to(dtype=cache_dtype)` 显式转换。

### 未解决 / 已知限制

1. **KV gather 仍有每步复制**：向量化消除了 Python 开销，但 gather 本身仍需将分散 block 数据复制到 dense tensor。彻底消除需要 flash_attn 2.5+ 的 `block_table` 支持（当前 flash_attn 2.3.6 不具备），或自写 Triton kernel。
2. **mixed benchmark 无 per-request EOS 截断**：`generate()` 不支持 per-request `max_new_tokens`，无法完整体现 continuous batching 的短请求提前释放优势。
3. **TPOT 是 amortized 值**：无单请求 p50/p95 延迟数据，与生产系统指标口径不一致。
