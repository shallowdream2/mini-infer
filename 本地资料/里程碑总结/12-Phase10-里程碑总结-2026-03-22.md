## 背景与目标

Agent 场景中大量请求共享相同前缀（system prompt、RAG 文档、few-shot 示例）。Phase 9 之前每个请求都从头 prefill，相同前缀的 KV 被重复计算。

Phase 10 目标：实现 block 粒度的前缀缓存（RadixAttention 风格），使第 2+ 个共享相同前缀的请求能复用已缓存的 KV blocks，跳过 prefix prefill 计算，量化 TTFT 收益。

### 验收标准逐条核查

| 标准 | 结果 | 说明 |
|------|------|------|
| 第 2+ 个共享前缀的请求 TTFT 显著低于第 1 个（可量化 speedup） | **达成** | hit TTFT=1139ms vs. miss TTFT=1468ms，speedup=**1.29×**（−22%），prefix=257 tokens / 1 block |
| 生成结果与无 prefix cache 完全一致（token-level） | **达成** | dry_run + GPU 双路验证；测试 `test_prefix_cache.py::TestEnginePrefixCacheE2E` 覆盖 |
| prefix cache 满时正确触发 LRU eviction，不影响正确性 | **达成** | `TestEvictLRU` 通过；evict 逻辑跳过 ref_count > 1 的 block |
| `pytest tests/` 全部通过 | **达成** | 100/100 通过（含 15 个新增 prefix cache 测试）|

## 已完成内容

### 核心实现

**`mini_infer/kv_cache.py`**

- `_compute_block_hashes()`：SHA-256 链式 hash（`hash[i] = sha256(prev_hash ‖ token_ids[i*bs:(i+1)*bs])`），替换了非确定性的 Python `hash()`
- `find_prefix_cache(token_ids)`：返回 `(cached_len, cached_phys_block_ids)`，按 block 对齐，末尾非整块不缓存
- `init_request_with_prefix(state, cached_len, cached_blocks)`：直接写入 block_table，跳过新分配；同步增加 ref_count
- `register_prefix_blocks_for_request(request_id, token_ids)`：prefill 结束后将新计算的 KV blocks 注册到 prefix cache
- `evict_lru_prefix_block()`：LRU eviction，只淘汰 ref_count == 0 的 block
- `prefix_cache_size()`：返回当前缓存持有的 block 数
- `swap_out()` 修复：swap 后清除 `state.prefix_cached_len = 0` 和 `state.prefix_cached_blocks = []`，防止 swap-in 后重用过期状态

**`mini_infer/request.py`**

- `RequestState` 新增字段：`prefix_cached_len: int = 0`、`prefix_cached_blocks: list[int]`

**`mini_infer/engine.py`**

- `_admit_with_prefix(state)`：admit 阶段查询 prefix cache，命中则 `init_request_with_prefix`，否则 `init_request`
- `_prefill_and_register(newly_admitted)`：分路 prefill（miss → `model_runner.prefill`；hit → `model_runner.prefill_with_prefix`），然后统一 `register_prefix_blocks_for_request`
- admission check 修复：`blocks_needed = ceil((suffix_len + max_out) / block_size)`（suffix 去掉 cached prefix），防止高命中率 workload 下过度拒绝准入

**`mini_infer/model_runner.py`**

- `prefill_with_prefix(state, cached_len, cached_blocks)`：从 block tensor 重建 prefix KV，只对 suffix 做 HF forward，写入 suffix KV，采样第一个 token

### 测试

- **新增** `tests/test_prefix_cache.py`：15 个测试
  - `TestFindPrefixCache`：miss、partial hit、full-prompt capping
  - `TestInitRequestWithPrefix`：block_table 结构、ref_count 增加、共享 block 不提前释放
  - `TestEvictLRU`：淘汰压力下的正确性、跳过 ref_count > 1 的 block
  - `TestPrefixHitPreemption`：un-admit 后 ref_count 恢复、re-admit 再次命中、swap_out 清除 prefix state
  - `TestEnginePrefixCacheE2E`：miss/hit 生成、cache size 可读、无 block 泄漏
- **修改** `tests/test_engine.py`（4 处）：`num_free_blocks() + prefix_cache_size() == initial_free`
- **修改** `tests/test_preemption.py`（1 处）：同上断言适配

### Benchmark

- **新建** `benchmarks/benchmark_prefix_cache.py`：支持 `--dry_run`（功能验证）和真实 GPU 模式（TTFT + 吞吐对比）

## 关键成就

1. **完整的 block 级前缀缓存链路**：从 `find_prefix_cache` 到 `register_prefix_blocks_for_request`，覆盖 miss/hit/evict/preemption 四条路径，而不是只实现 happy path。

2. **确定性 hash 设计**：用 `hashlib.sha256 + struct.pack` 的链式 hash（类似 radix tree 的前缀嵌入），替换了 Python `hash()` 的 PYTHONHASHSEED 问题，保证进程重启后 hash 一致。

3. **ref_count 语义完整**：cache 持有 + 每个 running 请求各持有一份引用，`evict_lru` 只淘汰引用归零的 block，避免了 use-after-free 类问题。

4. **admission check 修正**：命中 prefix 后 `blocks_needed` 仅计算 suffix，防止在高命中率 workload 下 engine 错误地拒绝准入（修复了一个影响正确性的设计 bug）。

5. **量化 TTFT 收益**：257-token prefix（1 block，block_size=256），RTX 4090 + Qwen2.5-7B 实测 TTFT −22%（1468ms → 1139ms）。符合预期：prefix 越长、output 越短，收益越大。

## 问题与风险

### 遇到的真实问题

1. **原始 hash 非确定性**：实现初期用 Python `hash()`，导致进程间/重启后 hash 不同，测试随机失败。通过换 SHA-256 解决。

2. **capping 逻辑导致 6 个测试失败**：4-token prompt + block_size=4 时，block-aligned capping 导致 cached_len=0（末尾全 token 不缓存）。这是预期行为，但测试 prompt 设计有误。解决方案：测试改用 5-token prompt 确保有 suffix。

3. **GPU 上 prefix_cache_size=0**：默认 shared_prefix 只有 39 tokens，低于 block_size=256。解决方案：用 engine 的 tokenizer 精确截断到 257 tokens（block_size+1），保证 1 个完整 cacheable block。

4. **GPU OOM**：首次 benchmark 设 `num_gpu_blocks=1024`，Qwen2.5-7B 加载后显存不足。降到 256 后正常。

### 未达成 / 部分达成

- **batch 吞吐无明显提升**：当前测试 workload（prefix=257 tokens，output=64 tokens）中 decode 步骤占主导，prefix cache 的节省量占比很低（speedup=0.99×）。这不是实现 bug，而是测试 workload 的局限性——真实 RAG 场景（prefix=1000+ tokens，output=16 tokens）会有显著提升。

### 仍未验证

- **多-block prefix（> 2 blocks）场景**：只测试了 1 block prefix；8-block（2048 token）的 radix 树深度命中未测
- **swap_out + swap_in 后 prefix 重建**：dry_run 验证了字段清零，但 GPU 场景下 swap-in 后 re-admit 并再次命中 prefix cache 的完整路径未做端到端验证
- **并发多请求共享同一 block 的 ref_count 竞争**：当前引擎是单线程，实际生产化场景需要加锁
