# Phase 6 里程碑总结：True PagedAttention（flash_attn + block_table）

本文件记录 mini-infer Phase 6 的目标、实现内容、验收标准达成情况和关键问题。

---

## 背景与目标

Phase 5 profiling 揭示了 decode_batch 的时间分布：model_forward 占 97-98%，gather_batch_kv 占 1.5-1.8%，write_decode_kv 占 0.1-1.1%。batch=8 吞吐为 HF 的 88.4%，还差 12%。

Phase 6 的核心目标：**用 flash_attn_with_kvcache 的 block_table 接口替换现有的"gather→DynamicCache→write_kv"三段路径**，让 attention kernel 直接从 block tensor 寻址，消除 gather 和 write_kv 两个独立步骤。

**预期提升（路线图原始估计）**：90-95% HF baseline（+2-7个百分点）。
**实际结果**：达到 **100.0%** HF baseline，超出预期。

## 关键成就

### 1. True PagedAttention 实现
Phase 1-5 的 decode 路径是：`gather → DynamicCache → model.forward() → write_kv`。Phase 6 消除了所有中间步骤，flash_attn_with_kvcache 直接读写 block tensor，无拷贝，无 Python 循环。

### 2. 吞吐达到 HF baseline 的 100.0%
| 指标 | Phase 3 | Phase 6 | HF baseline |
|------|---------|---------|-------------|
| Throughput (tok/s) | 361.3（88.4%）| **406.3（100.0%）** | 406.4 |
| TTFT (ms) | 43.8 | **18.8** | 19.9 |
| TPOT (ms/tok) | 21.1 | **2.46** | 2.46 |
| model_forward (ms/step) | 17.89 | **17.06** | — |
| gather_batch_kv | 0.31ms/step | **0** | — |
| write_decode_kv | 0.19ms/step | **0** | — |

### 3. flash_fwd_splitkv_kernel 确认生效
profiler top-20 中新出现 `flash_fwd_splitkv_kernel`：
- 调用次数：29步 × 28层 = 812次（精确匹配）
- 单次耗时：8.72μs/call
- 确认每层每步都在走 flash_attn 路径

## 遇到的问题与坑点

### 坑点 1：`.item()` 在 28 层内各触发一次 CPU-GPU sync（关键性能 bug）

**发现时机**：benchmark 结果异常（3.7% vs 期望 90%+），根因诊断需分析 profiler 的 527ms/step（Phase 5 的 17.9ms）。

**根因**：`patched_forward` 内 `max_kv_len = int(ctx.cache_seqlens.max().item()) + 1`，此行被 28 层各执行一次 = 28 次 CPU-GPU sync/step。每次 sync 约 18ms，合计 504ms，主导了 decode 耗时。

**修复**：将计算移到 `decode_batch()` 中（一次 `.item()`），通过 `PagedDecodeContext.max_kv_len: int` 传入所有层。修复后 benchmark 从 3.7% 恢复到 100.0%。

**教训**：在被 28 层各调用一次的函数内，任何涉及 CPU-GPU sync 的操作都是性能杀手。`.item()`、`.numpy()`、`print(tensor)` 均会触发同步。

### 坑点 2：block_size 改为 256 后未同步更新 num_gpu_blocks

`profile_decode.py` 原设置 `num_gpu_blocks=2048`，Phase 5 时 block_size=16 对应 1.79 GB KV cache，可接受。Phase 6 切换到 block_size=256 后，2048 块需要约 28 GB，直接 OOM。修复：改为 `num_gpu_blocks=200`（51200 token 容量，profiling 场景够用）。

### 坑点 3：flash_attn block_size 必须是 256 的倍数

flash_attn_with_kvcache 内核要求 `k_cache.shape[1] % 256 == 0`，运行时才报错：
```
RuntimeError: Paged KV cache block size must be divisible by 256
```
默认 block_size 从 16 改为 256。现有单元测试显式传 `block_size=4`（dry_run 路径），不受影响。

### 坑点 4：benchmark 结果发现方式（不经过 review 直接 benchmark 才暴露）

`.item()` 问题在三轮 infer-review 中均未被发现，仅在 benchmark 运行后发现异常结果才追查到根因。原因：这是**性能问题而非正确性问题**，review 只能静态分析代码，无法在不跑 GPU 的情况下量化 28 次 sync 的实际开销。
