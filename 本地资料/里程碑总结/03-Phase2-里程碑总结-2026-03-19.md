# Phase 2 里程碑总结：Paged KV Cache + Continuous Batching + Batch Decode

这个文件记录 mini-infer Phase 2 的完整实现过程、关键决策和 benchmark 结果，作为阶段收尾的正式总结。

## 背景与目标

Phase 1 完成了基于 HuggingFace `generate()` 的最小串行推理链路：每次请求单独调用 `model.generate()`，无 KV cache 复用，无并发。Phase 2 的目标是实现工业级推理引擎的核心机制：

**目标**：
1. Paged KV Cache：用固定大小的 GPU block tensor 池管理 KV，支持 Block Table 映射
2. Batch Decode：所有运行中的请求合并为一次 GPU forward，不再串行逐条
3. Continuous Batching：新请求在现有请求 decode 过程中动态加入，不等待整批完成

**验收标准**：
- smoke test 通过（dry_run 模式）
- KV cache 单元测试通过（5 个测试）
- 真实 GPU 上 batch=1/4/8 基准测试可运行
- TTFT 与 HF baseline 相差 < 10%

## 关键成就

### 1. 完整的 Paged KV Cache 实现
实现了预分配 GPU block tensor 池（`k_cache[l][block_id, slot, num_kv_heads, head_dim]`），通过 `BlockTable` 管理每个请求的物理块映射，`FreeBlockPool`（deque）管理空闲块。这是 vLLM 核心机制的简化复现。

### 2. 工作的 Batch Decode
`decode_batch()` 将多个请求的 KV 从 block 池聚合为 dense tensor（左填充对齐），执行一次批量 forward，再写回新 token 的 KV。验证数据：batch=8 的均摊 TPOT 为 5.00ms，低于 batch=1 的 20.24ms，证明批处理有效。

### 3. Continuous Batching 主循环
每次迭代动态接入等待队列中的请求（受 max_batch_size 和 KV 块可用量限制），新请求在现有请求 decode 途中加入。这是区别于静态 batching 的核心设计。

### 4. OOM 安全
- 提前检查请求所需块数，不足时快速失败（不死循环）
- try/finally 确保异常时归还所有 KV 块，防止显存泄漏

### 5. Benchmark 完整跑通
| batch | mini-infer | HF baseline | 比率 |
|-------|-----------|-------------|------|
| 1 | 49.4 tok/s | 56.2 tok/s | 87.9% |
| 4 | 135.2 tok/s | 210.5 tok/s | 64.2% |
| 8 | 201.0 tok/s | 408.9 tok/s | 49.1% |

TTFT 与 HF 基本一致（18.7–19.0ms），说明 prefill 链路正确，overhead 主要在 decode 阶段。

## 问题与风险

### 已遇到并解决的问题

1. **无限循环 bug**：engine.py 原始设计中，如果 KV 块不足且没有其他请求在跑，会死循环等待块释放。通过检查 `num_running==0 and not newly_admitted` 条件，改为立即 raise RuntimeError。新增测试 `test_engine_oom_raises_not_loops` 覆盖。

2. **num_kv_heads 错误默认值**：Phase 1 知识笔记误记 Qwen2.5-7B 有 8 个 KV heads，实际是 4（GQA：28 Q heads，4 KV heads）。导致 `k_cache` shape mismatch error。修正 `config.py` 默认值和 `benchmark_mini.py`。

3. **DynamicCache 兼容性**：transformers 4.43.4 弃用了 tuple 格式的 `past_key_values`，但通过 `DynamicCache.from_legacy_cache` 仍可工作，有弃用 warning。Phase 3 可迁移到原生 `DynamicCache` API。

4. **model_runner.py 重复方法定义**：第一次写入时不小心产生了两个 `decode_batch()` 方法定义（Python 取最后一个，导致第一个实现被覆盖）。通过完整重写文件修复。

5. **GPU 占用阻塞**：ollama 进程占用 GPU 显存，无法加载 Qwen2.5-7B。等待其释放后在 GPU 0 运行测试。

### 已知局限性

1. **`gather_batch_kv()` 每步复制开销**：每个 decode step 都从 block tensor 复制 KV 到新的 dense tensor，这是当前吞吐量低于 HF 的主因。实际的 PagedAttention 会用自定义 CUDA kernel 直接在 block pool 上做 attention，避免复制。

2. **TPOT 口径差异**：mini-infer 报告的 TPOT 是批次均摊值，HF 是单请求延迟，不可直接比较。

3. **左填充 batch**：当请求序列长度差异很大时，填充开销会显著增加显存和计算量。

4. **未测试混合长度请求**：Continuous batching 的优势在混合长度场景下更显著，本次 benchmark 用同质 prompt 未充分展示。
