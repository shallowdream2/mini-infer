# Phase 11 里程碑总结 — Speculative Decoding

日期：2026-03-22

---

## 背景与目标

在完成 Phase 10（Prefix Caching）后，调度器和 KV cache 管理已经成熟，是引入推理算法创新的合适时机。

Phase 11 的目标是在 mini-infer 中实现 **Speculative Decoding（投机解码）**：使用小型 draft model（0.5B）批量预测 K 个候选 token，再用大型 target model（7B）一次 forward 并行验证，通过 modified rejection sampling（Leviathan et al. 2023）保证输出分布等价于 target-only 生成，同时期望通过减少 target forward 次数提升吞吐。

本阶段的最小验收口径（来自路线图 + CLAUDE.md）：
1. draft + target 双模型主链路跑通，生成语义合理的文本
2. 可测量 acceptance rate（α）
3. 给出吞吐提升（或如实说明回退成本）

### 修复（review 发现）

- **KV 位置偏移 bug**：`_get_prefill_last_logit` 用 `use_cache=False` 运行 target，first_token 的 KV 从未写入 block tensor，导致后续所有 `spec_verify_target` 在少 1 token 的上下文中运行。修复方案：将该调用替换为 `spec_advance_target_kv([first_token])`，同时写 KV 并返回 logit，删除 `_get_prefill_last_logit` 方法。

## 关键成就

### acceptance_rate = 55.85%（K=4, greedy）

- 410 个 draft token 中 229 个被 target 接受
- 验证了 modified rejection sampling 的正确性：draft 预测与 target 分布在 55% 的位置重合
- greedy (temperature=0) 下 acceptance_rate 反映两个模型"思路一致"的程度，55% 是 0.5B→7B 的合理水平

### rejection sampling 正确性验证

- 4 条 prompt 输出语义合理（与 target-only 独立生成的文本风格一致）
- 输出分布理论等价于 target-only（由 Leviathan rejection sampling 算法保证）
- dry_run 路径：13 个测试全通过，acceptance_rate=100%（probs 全 0 时直接接受路径）

### 跨设备张量对齐实现

- draft 在 cuda:0，target 在 cuda:1，rejection sampling 中需要对齐 device 和 vocab_size（0.5B: 151936 vs 7B: 152064）
- 通过 `_align_draft_prob` 同时处理 `.to(device)` 和 vocab pad/truncate

## 问题与风险

### 1. spec v1 吞吐低于 target-only（0.65×，未达成"吞吐提升"）

这是 v1 双 forward 设计的**预期代价**，已在 spec_engine.py docstring 中标注：

> target 验证后通过 spec_advance_target_kv 二次 forward 写入 KV（非最优，可优化为一次 forward）

根因：
- 每轮接受约 2.3 个 token，但需 2 次 7B forward（verify + advance）
- 等效计算量 ≈ target-only，加上跨设备同步 + Python loop overhead → 实际 0.65×
- v2 优化：合并 verify + advance 为一次 forward，预期 acceptance_rate=55% 时理论 speedup ≈ 1.4×

### 2. 本次 debug 周期过长（非代码问题，流程问题）

在 GPU 验证阶段出现三处失误叠加：
- 没有在对话开始时读 `project_env_state.md`，导致重蹈已知的"7B snapshot 路径不完整"坑
- 后台进程 stdout 被 pipe 缓冲，误判为"进程挂住"
- 用 `sleep 90` 等待，而非增量验证

这些问题与代码无关，反映了会话管理和验证策略的缺陷，已事后分析记录。

### 3. throughput 口径为近似值

benchmark 使用 word count 近似 token count，真实 tok/s 可能偏低 10-20%（中文/代码场景偏差更大）。TTFT 未计时。
