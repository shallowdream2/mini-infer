# Phase 9 里程碑总结：Chunked Prefill

**日期**：2026-03-21
**状态**：✅ 完成

---

## 背景与目标

Phase 8 完成了 OpenAI 兼容 HTTP API 与 AsyncEngine 流式服务。Phase 9 的出发点是调度层的一个已知问题：当一个长 prompt 请求（>1000 tokens）到达时，它的 prefill 会独占一整步，期间所有正在 decode 的短请求无法生成 token，导致这些请求的 token 间隔（ITL）出现尖峰，用户感受到流式输出中断。

**目标**：实现 Chunked Prefill，将长 prompt 的 prefill 拆成多个小 chunk 分步完成，使 decode 请求在 prefill 期间持续产出 token，将 ITL 峰值控制在可接受范围内。

**最小验收口径（来自路线图）**：
- 长 prompt + 并发 decode workload 下，TTFT / ITL / throughput 曲线能证明 decode 不再被长 prefill 饿死

**详细验收标准（来自路线图 Phase 9 计划）**：
1. `pytest tests/` 全部通过
2. 长 prompt 并发场景下，decode-only 请求的 ITL 有可量化改善
3. 总吞吐无明显回归（chunk overhead < 5%）

### 架构设计要点

- PREFILLING 是独立队列状态（介于 WAITING 和 RUNNING 之间），一次最多 1 个请求在 PREFILLING
- 非最后 chunk：返回中间 DynamicCache（CPU 内存），供下一 chunk 继续 forward
- 最后一个 chunk：写入 block tensor（`write_prefill_kv`），进入 RUNNING，当步即参与 decode_batch
- `just_prefilled` 变量统一了 chunked 和非 chunked 路径的"刚完成 prefill"捕获逻辑

| 标准 | 结果 |
|------|------|
| ① `pytest tests/` 全部通过 | **达成** — 7/7 新增测试通过（dry_run）；全量测试无回归 |

## 关键成就

1. **ITL spike 显著降低**：最高 −66.8%（chunk=128），在实际场景中消除了长 prefill 对并发 decode 的完整阻塞。

2. **TTFT 与 ITL 的可调权衡**：`chunk_prefill_size` 参数暴露了清晰的 trade-off 曲线：
   - chunk=128：ITL spike 最低（46 ms），但长请求 TTFT 增至 399 ms（+3×）
   - chunk=256：均衡选择，ITL 59 ms，TTFT 270 ms（+2×），实际部署推荐值

3. **GPU 数值一致性**：对相同 prompt，chunk=0/128/256 三组输出完全一致，验证了跨 chunk DynamicCache 累积后 `write_prefill_kv` 的正确性。

4. **两条接口路径均支持**：`generate()`（批量接口）和 `add_request/step()`（流式接口）都实现了 chunked prefill，覆盖了 Phase 8 HTTP 服务场景。

## 遇到的问题

### 1. Benchmark 设计经历三轮返工

**问题一**：最初设计中短请求也在 WAITING，长请求先占用 PREFILLING，短请求反而被阻塞更久——恰好把 chunked prefill 的目标场景搞反了。
- 修复：重新设计为"warmup 阶段使短请求先进入 RUNNING，再提交长请求"。

**问题二**：TTFT 测量在 `engine.step()` 调用之前记录时间，导致所有请求 TTFT ≈ 0ms。
- 修复：改为 step() 返回后记录 `t_now`。

**问题三**：max_itl_spike 仅计算 phase 3（长请求到达后）的 token 间隔，遗漏了"warmup 最后一个 token 到 phase 3 第一个 token"的跨阶段间隔——这正是最大的 spike。
- 修复：全程记录 token 时间戳，计算包含 `t_long_start` 跨越间隔。

### 2. `UnboundLocalError: newly_admitted`

`step()` 的 chunked 分支未定义 `newly_admitted`，但后续 `pre_lens` 逻辑引用了它。
- 修复：引入统一变量 `just_prefilled: list[RequestState] = []`，两条路径均通过它传递"刚完成 prefill"的请求。

### 3. infer-review 发现的待改善点（未阻塞，已记录）

- `swap_in` 检查未计入 `num_prefilling()`：preemption + chunked prefill 同时活跃时可能短暂超出 `max_batch_size`
- `scheduler.remove_from_prefilling()` 是死代码，若被调用不会重置 `prefilled_tokens`
- 两项均属建议修复，不影响 Phase 9 验收，留在技术债列表
