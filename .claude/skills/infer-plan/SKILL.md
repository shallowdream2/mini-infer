# infer-plan

这个文件用于为当前任务输出阶段计划、执行顺序和验收标准。

把附加文本视为当前任务描述，按以下结构输出计划。**默认不改代码**，除非用户明确要求直接实现。

## 输出结构

### 1. 动机（承接上一阶段）

说明上一阶段发现了什么，导致需要做本阶段的工作。引用具体的数据、发现或已知技术债。

### 2. 前置条件

列出开始实现前必须满足的外部条件（依赖安装、环境验证、架构决策等）。

每条附上验证命令，格式：
```
条件：flash_attn >= 2.5 已安装
验证：python -c "from flash_attn import flash_attn_with_kvcache; print('ok')"
```

**未满足前置条件时，输出计划但提示用户先满足条件再调用 infer-implement。**

### 3. 目标

一句话说清楚本阶段完成后系统能做什么新的事，或性能达到什么指标。

### 4. 范围

**要做：**
- 具体到文件级别的改动（新增 / 修改 / 删除）

**不做（同样重要）：**
- 明确排除的内容，避免范围蔓延

**接口变更影响（若有）：**
- 哪些现有文件/测试会被破坏性影响，以及为什么这是可接受的

### 5. 分步实现顺序

拆解为 3-5 个可独立验证的步骤，每步给出验证方式：

```
步骤 1：…
  验证：python -m pytest tests/xxx.py -k "test_yyy"

步骤 2：…
  验证：python -c "from mini_infer.xxx import yyy; yyy()"
```

### 6. 验收标准

至少 2 条可量化标准 + 1 条正确性验证：

- 量化：`batch=8 throughput ≥ 95% HF baseline`（数字来自 benchmark_mini.py）
- 正确性：当前改动对应的 dry_run / 单元测试通过；如果改动跨多个模块或公共接口，再升级为组合测试
- profiling 验证：`profile_decode.py` 中目标操作的 CUDA 时间降至预期值

### 7. 风险与回退

| 风险 | 概率 | 回退方案 |
|------|------|---------|
| … | 中 | … |

## 质量要求

完成输出后，**必须在输出末尾附上 CHECKLIST.md 的逐项自查结果**，格式如下：

```
## 自查结果（CHECKLIST.md）

- [x] 动机引用了上一阶段的具体数据
- [x] 前置条件附带验证命令
- [ ] ...（若某项未满足，说明原因）
```

不得只说"已按清单检查"，必须逐项列出 ✓ 或 ✗ 及原因。

## 完成后

CHECKLIST 自查通过后，在 `CLAUDE.md` 的当前阶段进度表中将 `infer-plan` 步骤标为 ✓。
