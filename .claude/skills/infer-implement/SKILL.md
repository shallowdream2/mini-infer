# infer-implement

这个文件用于在当前项目中实现具体功能或修改现有代码。

把附加文本视为当前实现任务，并遵守以下要求：

## 开始前必做

1. **读计划**：找到本阶段 infer-plan 的输出，确认当前要实现的是哪个步骤
   - 如果当前对话中找不到 infer-plan 输出（例如使用了 `/clear`），先检查 `本地资料/Claude计划/00-长期路线图.md` 中对应阶段的"分步实现顺序"，或提示用户重新调用 `infer-plan` 后再继续
   - **不得在没有明确计划的情况下开始实现**
2. **验证前置条件**：如果计划中列了外部依赖（如 flash_attn），先验证已满足，再动代码
3. **读相关文件**：实现前必须读将要修改的文件，理解现有接口和约定

## 实现要求

- 只改与当前任务直接相关的文件，不顺手重构其他部分
- 优先最小可运行实现：先让它能跑，再让它好
- 如果本步骤涉及**破坏性接口变更**（删除旧函数、改变参数格式），先在注释里说明"旧接口已被替换，因为…"

## 验证要求

每个实现步骤完成后必须给出与当前改动匹配的验证：

- **dry_run 路径**（无 GPU）：优先运行与当前改动直接相关的最小测试；如果改动跨多个模块、公共接口或阶段主链路，再升级为组合测试或 `python -m pytest tests/`
- **GPU 路径**（有 GPU）：对 GPU / 推理逻辑修改，至少跑一次与改动直接相关的真实路径（如 `engine.generate()`、对应 benchmark 或 profile 命令）并说明结果
- 如果环境不满足验证条件，**明确说明**原因和缺失的条件，不得伪造结果

## 完成后汇报

每轮 implement 结束，说明：
1. 改了什么、为什么这样改（对照计划中的步骤编号）
2. 验证结果（附命令和输出摘要）
3. 还差什么（下一轮要做的，或需要 review 关注的点）

## 完成后

`infer-implement` 可多轮迭代，**不是**每轮都更新进度表：
- 如果本轮完成后还需要 `infer-review` → 改代码 → 再次 `infer-implement`，**本轮不标 ✓**
- 只有当 `infer-review` 确认无阻塞性问题后，才将进度表中的 `infer-implement` 步骤标为 ✓

## 硬性约束

- **不得在没有 infer-plan 的情况下开始实现**
- **未满足计划中的前置条件时，不得写依赖该条件的代码**（先提示用户满足条件）
- 发现计划有误时，先停下来描述问题，不要自行修改计划后继续——等用户确认

## 前置条件多次失败时的降级路径

如果前置条件在合理尝试（≥3 次）后仍无法满足，**必须停下来回到 infer-plan 修订计划**，而不是无限重试或强行跳过。修订方向：

- 环境问题（编译失败、版本不兼容）：升级依赖版本，或修改方案绕过该依赖（如改用 PyTorch 原生 API 代替 flash_attn）
- 方案假设有误（接口不存在、API 变更）：调整实现方案，而不是等待环境变化
- 拆分阶段：如果问题来自阶段范围过大，拆成两个阶段，先做不依赖该条件的部分
